# CT-07 — Duplicate identifiers

| | |
|---|---|
| **Case** | `CT-07` |
| **Specification** | [SPEC-MAS-001 §10](../spec/SPEC-MAS-001.en.md#ct-07--duplicate-identifiers) v1.1.0 |
| **Reference data** | [`reference-data.csv`](../code/src/test/resources/reference-data.csv), line `CT-07` |
| **Discriminating** | **Yes** — nothing else looks at identifier uniqueness |

## What it covers

| Item | |
|---|---|
| [`E-MAS-003`](../spec/SPEC-MAS-001.en.md#e-mas-003) | Two components carry the same `component_id` → reject |

## The data

`target_batch_mass = 1.000 kg`, `balance_step = 0.001 kg`

| Component | Fraction |
|---|---|
| `CMP-A` | 0.500000 |
| `CMP-A` | 0.500000 |

Fractions sum to exactly 1, so `E-MAS-001` is satisfied. **Expected: rejected with
`E-MAS-003`.**

## Why the case exists

Because the tie-break of [`RG-050`](../spec/SPEC-MAS-001.en.md#rg-050--allocation-of-the-residual)
is *"the smallest identifier"*, and with two identical identifiers that phrase names two
different components. **The rule stops being a rule.**

This is what makes it a business rejection rather than input hygiene. Without the check,
nothing crashes: the batch computes, the residual is allocated to one of the two rows, and
which one depends on the traversal order — reintroducing exactly the order-dependence that
`INV-04` forbids and that `RG-050` was written to remove.

Note that this case is *ordered* in the specification after `E-MAS-001` and the
implementation checks them in that order. A recipe both unbalanced and duplicated is
rejected with `E-MAS-001`. That ordering is arbitrary but it is fixed, so the reported code
is reproducible.

## What it does not test

| | |
|---|---|
| More than two duplicates | Only a pair is exercised |
| Case or whitespace variants | `CMP-A` and `cmp-a` are different identifiers to this implementation, and the specification says nothing about it. **That is an open hole**, not a decision |
| Any nominal behaviour | The calculation is never entered |
