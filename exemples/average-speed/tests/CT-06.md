# CT-06 — A tie exactly at the half

| | |
|---|---|
| **Case** | `CT-06` |
| **Specification** | [SPEC-SPD-001 §10](../spec/SPEC-SPD-001.en.md#ct-06--a-tie-exactly-at-the-half) v1.1.0 |
| **Reference data** | [`reference-data.csv`](../code/src/test/resources/reference-data.csv), line `CT-06` |
| **Discriminating** | **Yes** — and it is the only case that decides either rounding parameter |

## What it covers

| Item | |
|---|---|
| [`RG-030`](../spec/SPEC-SPD-001.en.md#rg-030--average-speed) | Average speed |
| [`P-01`](../spec/SPEC-SPD-001.en.md#p-01) | Rounding mode of the published speed — `HALF_EVEN` |
| [`P-02`](../spec/SPEC-SPD-001.en.md#p-02) | Decimals of the published speed — 1 |
| [`INV-01`](../spec/SPEC-SPD-001.en.md#inv-01) | The result lies between the slowest and the fastest leg |

## The data

| Leg | Distance | Speed | Duration |
|---|---|---|---|
| 1 | 30 km | 5.0 km/h | 6.000000 h |
| 2 | 44 km | 22.0 km/h | 2.000000 h |

```
total_distance = 30 + 44           = 74 km
total_duration = 30÷5 + 44÷22      = 8 h
quotient       = 74 ÷ 8            = 9.25            exactly, on the tie
average_speed  = ROUND(9.25, 1, HALF_EVEN)          = 9.2 km/h
```

**Expected: `average_speed` = 9.2 km/h.**

## Why the case exists

Because before it, **`P-01` was decided by nothing**.

The rounding mode had been chosen by the fleet operations manager, written into the
parameter table with an effective date, implemented in the code and reported as covered.
Five reference cases ran through it. Not one of them produced a quotient that a change of
mode would move: CT-01 gives exactly 40, CT-03 exactly 80, CT-04 exactly 9.1. Swap
`HALF_EVEN` for `HALF_UP` in the implementation and the whole suite stays green.

A parameter in that state is worse than an undocumented one, because the paperwork says it
is under control.

This case puts the unrounded quotient exactly on the half, where the mode is the only thing
that decides:

| Mode | Publishes |
|---|---|
| `HALF_EVEN` — the specified one | **9.2** — 2 is the even neighbour |
| `HALF_UP` | 9.3 |

It decides `P-02` at the same time: at two decimals the answer would be 9.25, so the number
of published decimals is arbitrated here too.

> **Both durations are exact, and that is deliberate.** 30 ÷ 5 = 6 and 44 ÷ 22 = 2, with no
> tail to lose. Had a duration been non-terminating, any implementation's working precision
> would have nudged the quotient a hair off 9.25 — both modes would then agree and the case
> would go on passing while testing nothing at all. **A case built on a tie has to reach
> that tie exactly**, or it quietly becomes CT-02.

## How the harness knows

The test does not take the claim on trust. For every nominal case it recomputes the result
under the *other* rounding mode and under one more decimal, and reports which parameters
that case actually arbitrates:

```
| `CT-06` | OK | 9.2 km/h · discriminates: the naive mean would give 13.5 km/h
                 · decides `P-01` — `HALF_UP` would publish 9.3
                 · decides `P-02` — one more decimal would publish 9.25 |
```

The [test report](../reports/TEST-REPORT.md) closes with a table of the parameters and
whether **any** case decides them. A parameter nothing arbitrates is printed as
*its value is never arbitrated* — a hole, stated where it will be seen.

## What it does not test

| | |
|---|---|
| Where the rounding happens | Both durations are exact, so rounding them early costs nothing here. `RG-010` is stated, not tested |
| The other tie direction | 9.25 rounds **down** under `HALF_EVEN`. A quotient of 9.35, which rounds **up** to 9.4, would be its mirror. No case covers it |
| The rejection path | See [CT-05](CT-05.md) |
